# Project Datasets & Storage Architecture

This directory houses the Medicare claims tables, NFHS-5 survey screening data, DuckDB columnar database, and SQLite investigation workspace.

## Directory Structure

```text
data/
├── medicare/                   # Raw Medicare claims and provider CSVs
│   ├── Train-1542865627584.csv
│   ├── Train_Beneficiarydata-1542865627584.csv
│   ├── Train_Inpatientdata-1542865627584.csv
│   ├── Train_Outpatientdata-1542865627584.csv
│   ├── provider_level_features.csv
│   └── final_model_comparison.csv
├── processed/                  # Optimized Parquet tables (compressed)
│   ├── claims.parquet          # 558,211 inpatient & outpatient claims with screening flags
│   ├── beneficiaries.parquet   # 138,556 Medicare patient demographic & condition profiles
│   ├── providers.parquet       # 5,410 healthcare providers with 10 features & ML risk tiers
│   └── eval_predictions.parquet # 80/20 stratified provider holdout scores
├── nfhs/                       # National Family Health Survey (NFHS-5) module
│   ├── nfhs5_screened_sample.parquet
│   └── nfhs5_rule_summary.json
├── claims_fraud.duckdb         # Columnar, indexed DuckDB analytical store (<10ms queries)
└── investigation_workspace.db  # ACID-compliant SQLite investigation case management database
```

## Dataset Segregation & Ethical Integrity

- **Medicare Claims**: Provider `PotentialFraud` label is provider-level based on historical audit/exclusion lists. Claims inherit provider risk context, but are not automatically declared fraudulent.
- **NFHS-5 Survey**: Maintained strictly separate. There are no shared identifiers between Indian public health survey respondents and US Medicare beneficiaries.
- **Claim-Level Ground Truth**: Public CMS datasets do not contain verified individual-claim fraud labels due to patient privacy laws (HIPAA). The system implements transparent rule-based screening indicators (reimbursement outliers, duplicate billing, duration anomalies) rather than fabricating synthetic claim labels.
- **Provider Evaluation Split**: `eval_predictions.parquet` is generated by `scripts/generate_eval_data.py`. The script makes a stratified 80/20 provider split, fits each evaluation estimator on the training partition only, and stores scores only for held-out providers. The full-data production model artifacts are separate and must not be used to claim holdout performance.
- **Currency**: Medicare source/model monetary values remain USD. Display conversion and INR formatting are centralized in `src/preprocessing.py`; `CLAIMS_DASHBOARD_USD_TO_INR` configures the rate (default `83.0`) and `CLAIMS_DASHBOARD_FX_EFFECTIVE_DATE` supplies its provenance label. The default is illustrative, not a current market quote. Reports keep source USD amounts alongside INR conversions and the rate metadata.
- **Investigation cases**: The SQLite workspace persists one case per `(target_type, target_id)`, with priority/status, reasons, observations, dated notes, and audit history. A case status is a workflow label, not a fraud finding.
- **Screening reconciliation**: Stored reimbursement-outlier flags use an inclusive `>=` cutoff in the old preparation artifact, while the current documented rule uses strict `>` type-specific p99. The Screening page recomputes rules from the source records and displays the differences instead of silently treating old stored flags as current truth.
- **NFHS benchmark**: Only the screened 35,000-record sample is available for record-level validation. The nationwide counts in the JSON file are recorded summary values and cannot be recalculated without the full source data.
